Issue for Person B
Title: Medicine photo upload — OCR identification + search polish
Description
Add photo-based medicine identification using Google Vision OCR, and finish out the medicine search frontend
pages. Users should be able to either type a medicine name or upload a photo of a medicine package and get
matched results.
Tasks
•
Backend: config/googleVision.js and config/cloudinary.js — set up API clients using keys from .env
•
Backend: services/ocrService.js — send uploaded image to Google Vision, extract text
•
Backend: services/drugLookupService.js — take extracted text, search it against the Medicine collection
(reuse the same $or/regex pattern from medicineController.js)
•
Backend: controllers/ocrController.js + routes/ocrRoutes.js — POST /api/ocr/identify, accepts an image
upload (multer), returns matched medicine(s)
•
Frontend: pages/medicine-search.html + js/pages/medicineSearch.js — search bar UI, calls the existing
search endpoint, renders results with js/components/medicineCard.js
•
Frontend: pages/medicine-details.html + js/pages/medicineDetails.js — photo upload form, calls the new
OCR endpoint, shows matched medicine or a "no match found" message
Acceptance criteria
•
Typing a medicine name and searching returns real results from the database
•
Uploading a clear photo of a medicine label returns a reasonable match, or a graceful "not found" message if
it can't match
•
No crash on invalid/blurry uploads — a real user-facing error message instead
Notes
OCR is the highest-risk piece of the whole project — if stuck on image preprocessing (blur, glare, rotation), flag it in
the group chat early rather than late. Search-by-name should be finished and solid first, since it's the fallback if
OCR isn't ready in time.

3. One-Time Repo Setup (You Do This First)
From inside the project's root folder:
git init
git add .
git commit -m "Initial commit: Days 1-4 complete"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/tenaye-info.git
git push -u origin main
Then on GitHub → repo Settings → Collaborators → add your three teammates by GitHub username so they have
push access. Each teammate then clones it once:
git clone https://github.com/YOUR_USERNAME/tenaye-info.git
cd tenaye-info
4. Branching Strategy
•
main — always working, deployable code. Nobody commits to main directly.
•
Feature branches — one branch per issue, named clearly: feature/ocr-search, feature/chatbot,
feature/pharmacy-locator
•
Each person works on their own branch, pushes it, opens a Pull Request into main, gets it reviewed, then
merges.
5. The Workflow — Issue to Merge
Step 1 — You create the issue, assign the teammate
Use the three issue templates in Section 2 above, copy-pasted directly into GitHub's New Issue form.
Step 2 — They branch off an up-to-date main
git checkout main
git pull origin main
git checkout -b feature/chatbot
Step 3 — Work, committing in small chunks
git add src/controllers/chatbotController.js
git commit -m "Add chatbot controller with Gemini integration"
Step 4 — Push the branch
git push -u origin feature/chatbot
Step 5 — Open a Pull Request
1
On GitHub, click "Compare & pull request" on the pushed branch
2
Title it clearly, e.g. "Chatbot: Gemini integration"
3
In the description, write "Closes #3" (using the actual issue number) so the issue auto-closes on merge
4
Request a review from you (or another teammate) before merging

=== PAGE 6 ===
Step 6 — Review & Merge
A reviewer checks the diff on GitHub — does it run, does it follow the same pattern as existing code. Approve, then
"Squash and merge" to keep main's history clean. Delete the feature branch afterward.
Step 7 — Everyone syncs
git checkout main
git pull origin main
6. Handling Merge Conflicts
1
Git marks conflicting sections with <<<<<<<, =======, >>>>>>> markers in the file
2
Manually edit to keep the correct combined version, delete the marker lines
3
git add the fixed file, then git commit to complete the merge
Since each person owns mostly separate files, conflicts should be rare. The main shared-risk files are app.js and
package.json — pull right before editing those, push right after.
7. Suggested Daily Rhythm
•
Morning (10 min): quick sync — what's done, what's today, any blockers
•
During the day: work on your own branch, commit and push often
•
End of day (15 min): push, open PRs for anything finished, review and merge before the day ends — don't
let PRs pile up
